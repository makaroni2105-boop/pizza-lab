# ADR 001: Quick Mode と Lab Mode の2モード分離

**Status:** Accepted  
**Date:** 2026-07-06  
**Deciders:** Pizza-Lab 設計チーム

---

## Context（背景）

Pizza-Lab は「世界中のピッツァ職人を支援する AI プラットフォーム」として、以下の相反する要求を同時に満たす必要がある。

1. **厨房での毎日利用** — 30秒以内に今日のレシピを出したい
2. **生地の研究・実験** — 粉温、湿度、ミキサー詳細、粉ブレンド等を細かく設定したい

Dough Intelligence Engine（DIE）は15以上の入力項目を持つ。すべてを毎日入力させれば精度は上がるが、**便利になるほど確認項目が増え、使われなくなる**（MANIFESTO 第1条）。

過去の設計では1画面に全項目を載せる案があったが、営業中の職人と研究する職人では必要な深さが根本的に異なる。

---

## Decision（決定）

**Quick Mode（営業モード）と Lab Mode（ラボモード）の2モードに分離する。**

- 計算エンジン（DIE）は **1つを共有**
- UI・入力スキーマ・表示項目のみモードごとに分ける
- 店舗プロファイルが Quick Mode の入力を肩代わりする

```
同一 DIE エンジン
  ├── Quick Mode UI  → 入力 2〜4 項目 → 結果（30秒）
  └── Lab Mode UI    → 入力 15+ 項目 → 結果 + 分析
```

---

## Rationale（理由）

### 1. 30秒ルールの保証

Quick Mode の入力を2〜4項目に制限するには、残りの項目をプロファイルと推定値で補完する必要がある。全項目フォームと共存できない。

### 2. 「わからない」の許容

Quick Mode ではミキサー機種・回転数等を **表示すらしない**。Lab Mode では詳細設定可能。1画面では両立しない。

### 3. ユーザーの意図の分離

| ユーザー | 意図 | モード |
|----------|------|--------|
| 毎日仕込む職人 | 「今日の数字を出して」 | Quick |
| 生地を研究する職人 | 「この条件で実験したい」 | Lab |
| 両方 | プロファイル共有 | 両方 |

### 4. 開発優先順位の明確化

Quick Mode だけで v0.1 リリース可能。Lab Mode は v0.2 以降。1モードで全部作るより、早く「毎日使えるもの」を出せる。

### 5. 1エンジン2UI のコスト最小化

DIE ロジック（`lib/die/`）は共通。UI レイヤー（`app/quick/`, `app/lab/`）だけ分岐。重複実装を避ける。

---

## Alternatives Considered（検討した代替案）

### A. 1画面 + 詳細展開（アコーディオン）

```
基本入力（常時表示）
  └── [詳細を表示 ▼]  ← クリックで15項目展開
```

**却下理由:**
- 「詳細を表示」が目について、毎回展開を誘惑される
- 展開すると30秒ルールが破綻
- 営業中に「詳細設定し忘れ」不安を与える

### B. スマート自動モード（入力数で自動切替）

```
入力が少ない → Quick 的動作
入力が多い → Lab 的動作
```

**却下理由:**
- ユーザーが今どちらのモードか分からない
- 推定値使用の透明性が下がる
- デバッグ・テストが困難

### C. Lab Mode のみ（Quick なし）

**却下理由:**
- 毎日15項目入力は現実的でない
- MANIFESTO「30秒以内」に反する
- 最初のユーザー（自分自身）が毎日使わなくなる

### D. 完全に別アプリ

**却下理由:**
- プロファイル・Learning データの共有が複雑
- 開発・保守コストが2倍

---

## Consequences（結果）

### ポジティブ

- Quick Mode で30秒レシピが保証される
- Lab Mode で研究機能を制限なく提供できる
- v0.1 を Quick のみでリリース可能
- DIE ロジックのテストは1箇所
- プロファイルが Quick の入力コストをゼロに近づける

### ネガティブ / トレードオフ

- 2つの UI を保守する必要がある（ただし DIE は共通）
- Quick → Lab への誘導 UX を設計する必要がある
- Lab Mode ユーザーが Quick の存在を知らない可能性 → トップで明示
- Quick ユーザーが Lab の存在を知らない可能性 → 結果画面に「詳細を調整」リンク

### リスクと対策

| リスク | 対策 |
|--------|------|
| Quick だけで Lab の価値が伝わらない | 結果画面に Lab 誘導リンク |
| Lab 設定が Quick プロファイルと矛盾 | プロファイルは Lab からも編集可。Lab の都度上書きは Run にのみ保存 |
| 2モードで Learning データが分裂 | Learning は Shop 単位。モード共通 |

---

## Implementation Notes（実装メモ）

### フォルダ分離

```
app/quick/     → Quick Mode UI
app/lab/       → Lab Mode UI（v0.2）
lib/die/       → 共通 DIE エンジン
lib/quick/     → Quick 入力縮約・補完
lib/defaults/  → フォールバックロジック
```

### 入力スキーマ

- Quick: `QuickModeInput`（profile.schema.json）
- Lab: `DieInput`（今後 die-input.schema.json で定義）
- Lab 入力は Quick 入力のスーパーセット

### プロファイルの役割

Quick Mode は **プロファイルが入力の80%を担う**。初回セットアップ（5分・1回）の重要性が増す。
